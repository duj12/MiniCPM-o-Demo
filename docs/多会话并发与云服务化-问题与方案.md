# 多会话并发问题 & 人脸/IC 服务化方案

> 面向对象：**InteractionCore**、**Agent Platform**、**人脸服务（G1）** 的代码提供方
> 编写时间：2026-09-24
> 背景：编排服务（Orchestrator）需要在 **105** 上部署一套内部测试服务，与 **106**
> 上正在使用的服务**并存**。实测发现三方各自的全局状态会导致并发时互相踩。

---

## 一、问题总览

### 1.1 现象

在一台机器上单会话运行时一切正常。当 **105 和 106 同时跑活跃会话**时：

```
12:36:17  105: Agent 的 IC 目标已设为 192.168.89.105:50051
12:36:54  106: ⚠️ Agent 的 IC 目标正被另一个会话指向 192.168.89.105:50051
               （106 夺回 → 设为 192.168.89.106:50051）
12:38:06  106: ⚠️ 又检测到冲突（105 又抢回去了）
```

**结果**：Agent 的 IC 目标被反复抢占，**两边都可能在窗口期内把 Action 派错**。

更早的一个版本里，105 报给 Agent 的是 `127.0.0.1:50051` —— 而从 Agent（部署在
`192.168.89.102`）的视角看，`127.0.0.1` 是**它自己**。这会让两边的 Action 全部派错。

### 1.2 根因：三个「进程级全局状态」

```
                  ┌──────────────────────────────┐
   105 编排 ──┐   │  Agent Platform (.102:8081)  │
             ├──▶│  interaction_core_target     │  ← 全局一个值（问题 ①②）
   106 编排 ──┘   └──────────────┬───────────────┘
                                 │ 回连
                  ┌──────────────▼───────────────┐
                  │  InteractionCore (:50051)    │
                  │  Engine / InteractionState   │  ← 进程内全局一份（问题 ③）
                  └──────────────────────────────┘
```

| # | 组件 | 全局状态 | 后果 | 归属 |
|---|---|---|---|---|
| ① | **Agent** | `interaction_core_target` 只有一个值 | 后设置的覆盖先设置的，**最后开会的赢** | Agent Platform |
| ② | **IC** | `AgentSink` 发 Action 时**不带会话标识** | Agent 无法区分 Action 来自哪路会话 | InteractionCore |
| ③ | **IC** | `Engine` / `InteractionState` 进程内全局一份 | 同一 IC 上的多会话会互相踩状态 | InteractionCore |

### 1.3 已确认的边界

- **编排服务本身没问题**：每路会话是独立的 `OrchestratorSession`，天然并发安全。
- **问题 ③ 是「设计如此」**：IC 的既有假设是「一个 IC 服务一个会话」。编排服务侧
  有对应的「单一驱动者」闸门（`IC 被会话 X 接管 —— 会话 Y 暂停驱动 IC`）。
  **只要 105 和 106 各跑各的 IC，这一条不冲突。**
- **真正共享的只有 Agent（问题 ①②）**，而 Agent 不知道 Action 从哪来。

## 二、方案

### 方案 A（推荐）：让 Agent **无状态** —— 请求里带回调地址

**核心思想**：不再让 Agent 存「IC 在哪」，而是**每次请求告诉它**。

#### IC 侧改动（InteractionCore）

**关键事实：这个模式在 `interaction/runtime.py` 里已经有现成先例 —— 只是没用到 Agent 那一路。**

```python
# ExpressionSink（IC → 编排服务）—— 已经带 session 了 ✅
def __init__(self, target, *, timeout=5.0, session_id=None, ...):
    self.session_id = session_id

def _post(self, path, payload, *, timeout):
    headers = {"Content-Type": "application/json"}
    if self.session_id:
        headers["X-Session-Id"] = self.session_id     # ← 注入请求头
```

```python
# AgentSink（IC → Agent）—— 完全没有 session ❌
def __init__(self, target: str, *, timeout: float) -> None:
    self.target = target.rstrip("/")
    self._timeout = timeout
    # ← 没有 session_id

def on_answer(self, *, identity_id, display_name, transcript) -> None:
    self._send("on_answer", {
        "identity_id": identity_id,
        "display_name": display_name,
        "transcript": transcript,
    })
    # ← payload 里没有会话标识
```

**建议改动**（约 10 行）：

```python
class AgentSink:
    def __init__(self, target: str, *, timeout: float,
                 session_id: str | None = None,
                 callback_ic: str | None = None) -> None:
        ...
        self.session_id = session_id
        #: 本 IC 的**对外可回连地址**（不是 127.0.0.1！）
        self.callback_ic = callback_ic

    def on_answer(self, *, identity_id, display_name, transcript) -> None:
        self._send("on_answer", {
            "session_id": self.session_id,      # ← 新增
            "callback_ic": self.callback_ic,    # ← 新增
            "identity_id": identity_id,
            "display_name": display_name,
            "transcript": transcript,
        })

    # on_insert / on_yield / on_end 同理
```

> ⚠️ **`callback_ic` 必须是外部可回连的地址**，不能是 `127.0.0.1` / `localhost`
> —— 否则 Agent 会去连它自己。建议做成 IC 的启动配置项（如
> `--callback-ic 192.168.89.105:50051`），并配上**当前机器的实际地址**。

`grpc_server.py` 里 `make_agent_sink` / `serve()` 需把这两个参数透传下去
（`ExpressionSink` 已经有完全一样的透传链路，可照抄）。

#### Agent 侧改动（Agent Platform）

1. `POST /interaction/on_answer`（以及 `on_insert` / `on_yield` / `on_end`）
   **读取请求体里的 `callback_ic`**，回调时用它。
2. **删掉 `interaction_core_target` 这个全局状态**，或降级为「未提供
   `callback_ic` 时的兜底」。
3. 建议**原样回传 `session_id`**（或作为 `X-Session-Id` 请求头）到编排服务 ——
   编排服务靠它精确路由回复（见下）。

**收益**：Agent 完全无状态，天然并发安全，不再需要 `set_target`。

#### 编排服务侧

**无需改动。** `session.start` 已支持每会话指定 Agent 地址（`ic.agent_url`），
`orchestrator_replay.py` 有 `--ic-agent-url` 参数。

---

### 方案 B（过渡）：Agent 按 session 存 target

若 Agent 不方便立刻改成无状态：

1. `POST /interaction/set_target` 增加 `session_id` 字段
2. Agent 内部存 `dict[session_id, target]` 而非单个值
3. IC 侧改动与方案 A 相同（仍要带上 `session_id` 和本机地址）

**注意**：因为问题 ③（IC 的 Engine 全局），**一个 IC 只能服务一个会话**，
所以 session ↔ target 是一一对应的。

## 三、Agent → 编排服务的回复路由（已就绪，待验证）

编排服务定位回复目标会话的逻辑：

```python
# orchestrator/main.py  _find_session()
sid = req.headers.get("x-session-id") or req.query_params.get("session_id") or ""
if sid and sid in REGISTRY.sessions:
    return REGISTRY.sessions[sid]
# 未指定时，若本机只有一个活跃会话，走这个兜底
if not sid and len(REGISTRY.sessions) == 1:
    return next(iter(REGISTRY.sessions.values()))
return None   # → 404
```

**结论：编排服务这边支持精确路由，能力已经有了。**
但**是否生效取决于 Agent 回调时有没有带 `X-Session-Id`**。

我们已在 `_find_session` 里加了诊断日志，会打印：

```
[speak] 来自 192.168.89.102：X-Session-Id='...' ?session_id='...' → 命中/未命中（本机活跃会话 N 个：...）
```

**待 Agent 侧确认**：回调 `/v1/speak` 或 `/v1/speak/stream` 时，
是否携带了 `X-Session-Id`（或 `?session_id=`）请求头？

- 带了 → 并发安全 ✅
- 没带 → 多会话并存时会 404，**回复丢失**

## 四、人脸服务（G1）服务化

### 4.1 现状与痛点

人脸检测（G1）目前是**编排服务通过 CDLL 直接加载 `libsdk_stream.so`** 调用的
（见 `orchestrator/face/g1face_provider.py`）。这带来一系列部署问题：

| 问题 | 具体表现 |
|---|---|
| **ABI 绑定** | `.so` 依赖编译机的 OpenCV。106 是 Ubuntu 22.04（OpenCV 4.5），105 是 20.04（4.2），**二进制不通用** |
| **必须目标机重编** | 换机器就得 `bash build.sh` 重编一遍 |
| **C++ 运行库冲突** | 105 上实测：`libstdc++.so.6` 版本太旧（6.0.29 < 需要的）、`libffi` 与系统 `libp11-kit` 符号冲突 |
| **共享目录陷阱** | 代码在 NFS 上（105/106 同 inode），在共享目录编译会**直接覆盖另一台机器正在用的 `.so`** |

> 实测量化：本次为让 105 跑起来，花了**数小时**处理 OpenCV / libstdc++ / libffi
> 三类环境问题，最终方案是「拷源码到本地磁盘 + 在目标机重编 + `LD_PRELOAD` 系统
> libffi」。

### 4.2 建议方案：包成 HTTP/WS 服务

**仓库里已有现成模板**：`board-face-and-cloud-infer/cloud_infer_server.py`
是一个完整的 FastAPI 服务，**而且已经按 session 隔离**
（`_get_or_create(sid)` / `class Session`），提供了：

```
POST /push  /push_bin  /flush  /flush_bin
WS   /ws/infer  /ws/infer_bin
GET  /health
```

（注：那个服务做的是 TSE 目标说话人提取，不是人脸检测，但**服务形态可以直接照搬**。）

#### 建议的接口

```
POST /face/detect
  { "session_id": "...", "frame_jpeg_b64": "...", "t_ms": 1234 }
→ { "valid": true,
    "box": [l, t, r, b],
    "score": 0.86,
    "lip_state": "SILENT",          # SILENT | SPEAKING | GAP
    "dwell_ms": 3200,
    "interacting": true,
    "identity": { "uid": "...", "name": "...", "similarity": 0.91 } | null }

WS /face/stream          # 长连接流式，省每次 JSON 开销
GET /health
```

字段与现有 `FaceObservation`（`orchestrator/face/signals.py`）保持一致，
便于 provider 侧直接映射：

```python
@dataclass
class FaceObservation:
    t: int                                  # 会话采样轴时刻
    valid: bool = False
    box: Optional[tuple] = None             # (left, top, right, bottom)
    score: float = 0.0
    speaking: bool = False
    lip_state: str = "SILENT"               # SILENT | SPEAKING | GAP
    interacting: bool = False
    person_id: int = -1
    dwell_ms: int = 0
```

#### 编排服务侧改动

`g1face_provider.py` 现在是 CDLL 直调。**加一条远程分支即可，两种模式并存**：

```python
if cfg.face_service_url:
    return RemoteFaceProvider(cfg.face_service_url)   # HTTP/WS
else:
    return G1FaceProvider(g1_root)                    # 本地 CDLL（现状）
```

保留本地模式的原因：**设备端/机器人上本地直调延迟更低**（省一次网络往返 +
JPEG 编解码），而云端/测试环境走服务化。

### 4.3 收益

| 今天卡住的 | 服务化后 |
|---|---|
| OpenCV 4.2 / 4.5 ABI 不兼容 | 收敛到服务端**一个进程**，调用方不关心 |
| libstdc++ / libffi 符号冲突 | 同上 |
| 必须在目标机重编 `.so` | 调用方只需 HTTP |
| NFS 共享导致误覆盖他机 | 物理隔离，不再有这问题 |
| 每个调用方都要配环境 | 统一一个 URL |

## 六、给 Agent Platform 的两个具体问题

1. **`POST /v1/speak` 和 `/v1/speak/stream` 回调时，是否携带 `X-Session-Id`
   请求头（或 `?session_id=` 查询参数）？**
   这决定了多会话并存时回复是精确路由还是 404 丢失。

2. **`interaction_core_target` 能否改成无状态**（每次请求带 `callback_ic`），
   或至少按 `session_id` 分开存？
   当前它是进程级全局值，多个编排服务同时使用时必然互相覆盖。

## 附录：当前临时状态

在正式方案落地前，我们已做以下**缓解措施**（都已实测验证）：

- 编排服务汇报给 Agent 的地址改为**对外可回连的真实地址**
  （`ORCH_IC_ADVERTISE`），不再是 `127.0.0.1`
- 会话结束时归还到**共享的默认 IC**（`ORCH_IC_RESTORE`），不再把错地址留下
- 检测到 target 被别的会话抢占时**打印告警**（不阻断）
- 转储改为**客户端显式请求才落盘**，避免 replay 污染共享的 `orchdump/`

**当前限制：105 与 106 不应同时运行活跃会话**（串开是安全的）。
正式方案落地后可解除此限制。
