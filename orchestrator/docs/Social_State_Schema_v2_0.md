# Social State Schema 2.0

> 文档类型：感知状态协议 / 下游决策输入契约  
> 版本：2.0（设计稿）  
> 日期：2026-11-02  
> 适用链路：Qwen3-Omni 等音视频感知模型 → Social State 输出器（Omni-Jev）→ State Engine → Interaction Policy / Agent  
> 兼容策略：保留原有 8 个顶层字段名称；2.0 将字段值从自然语言行改为有类型的对象。

---

## 1. 设计目标与范围

Schema 2.0 的目标不是增加更多顶层状态，而是让同一份感知结果同时满足三类消费者：

1. **人读得懂**：保留自然语言描述和必要证据。
2. **程序能消费**：枚举、数组、数值、对象各有明确类型，不依赖逗号切分自然语言。
3. **状态可量化**：每个枚举槽位输出当前类别及其置信度；自由文本保留长尾细节。
4. **下游可决策**：本 Schema 只描述“观察到了什么”，不输出是否打断、是否主动交互等策略结论。

### 1.1 保留的 8 个顶层字段

| 字段 | 主要语义 | 时间类型 | 主要表达方式 |
|---|---|---|---|
| `ATTENTION` | 人物身体/头部朝向、视线目标、注意力相关活动 | 当前状态 | 多个正交枚举槽位 + 描述 |
| `ACTION` | 点头、摇头、挥手、指向等离散动作事件 | 瞬时事件 | 事件数组 + 时间范围 |
| `EMOTION` | 可见面部表情所呈现的表观情绪 | 当前状态 | 视觉枚举 + 可观察证据 |
| `FEATURE` | 人物衣着、配饰及其他可见外观特征 | 相对稳定状态 | 自由文本为主，少量标准标签 |
| `BEHAVIOR` | 站立、坐、行走、靠近、远离等持续行为 | 持续状态 | 姿态/运动枚举 + 生命周期 |
| `RELATION` | 多人数量、空间组织、互动对象及谨慎的关系推断 | 当前场景状态 | 可观察事实与推断分槽 |
| `ENV` | 视觉场景、光照、可见环境要素 | 场景状态 | 少量枚举 + 自由文本 |
| `POSITION` | 人物在画面中的位置及与物体的相对位置 | 当前空间状态 | 画面区域/检测框 + 自由文本 |

### 1.2 不纳入本 Schema 的内容

以下仍由专门的音频、ASR、检测、跟踪或会话模块提供，不应要求 VLM 从视觉描述中猜测：

- ASR 置信度、话轮结束置信度、识别文本、语言与语种切换；
- SNR、噪声底、突发噪声、重叠语音、VAD 和声学话轮状态；
- 语音情绪。`EMOTION` 在本 Schema 中只表示视觉表情；
- 人脸身份认证结果；
- 唇动、在场/离开等已有专用服务负责的检测结果；
- 云台角度、相机外参、世界坐标、精确米制距离和速度。

音频内容可以出现在全局 `description.audio` 中，但不能覆盖 `EMOTION` 的视觉证据边界。State 只表达感知结果，不包含交互策略答案或额外问题列表。

## 2. 核心设计原则

### 2.1 枚举与自由文本分工

- **枚举用于规则决策**：例如朝向、行为类别、情绪标签、光照等级。
- **自由文本用于保留长尾细节**：例如“胸前挂着红色工作证”“位于玻璃展柜左侧”。
- 不把颜色、款式、图案混成一个枚举维度。
- 不为了追求封闭枚举而丢弃模型实际观察到的细节。
- 对每个枚举槽位明确允许值；未知情况不能硬塞到最接近的类别。

### 2.2 观察事实与语义推断分开

例如“两人并排站立”是可观察事实，“两人是同事”是关系推断。Schema 必须分别存储，且推断值允许为“不确定”。

### 2.3 事件与状态分开

- `ACTION`：在某个时间范围内发生过的离散事件，事件可以已经结束。
- `BEHAVIOR`：当前持续存在的姿态/运动状态，必须有生命周期语义。
- `ATTENTION`、`EMOTION`、`FEATURE`、`ENV`、`POSITION`：当前状态或相对稳定信息。
- `RELATION`：当前多人场景中的关系状态，是否保留取决于人员跟踪与场景连续性。

### 2.4 全量快照不等于每个字段都必须重新推断

每轮可以输出完整 8 字段快照，但每个字段必须标明它是本轮观察、沿用历史、无法判断还是已经过期。编排层不得把 `retained` 误当成新观测。

### 2.5 不确定性必须显式表达

“没有看到”与“看到但无法判断”不同；“目标不可见”也不等于“目标不存在”。应使用统一状态元数据，不要把所有缺失情况都写成自然语言“不可见”。

## 3. 统一数据结构

推荐将完整模型输出组织为以下顶层结构：

```json
{
  "schema_version": "2.0",
  "session_id": "session-001",
  "turn_id": "turn-012",
  "media_window": {
    "start_ms": 12000,
    "end_ms": 15800
  },
  "description": {
    "summary": "用户正面向设备，短暂看向旁边的人后又看回屏幕。",
    "visual": "用户穿灰色针织上衣，戴黑框眼镜；画面右侧另有一人。",
    "audio": "用户说话，语气较平稳；音频事件由音频侧模块另行判定。"
  },
  "state": {
    "ATTENTION": {},
    "ACTION": {},
    "EMOTION": {},
    "FEATURE": {},
    "BEHAVIOR": {},
    "RELATION": {},
    "ENV": {},
    "POSITION": {}
  }
}
```

`description` 是 8 个 State 顶层键之外的可读描述信息，不改变 8 个 State 顶层键。若下游已有旧的 8 行 `render_state()` 接口，可以由适配层从 `state` 对象生成，不建议继续把 8 行字符串作为唯一内部真值。

### 3.1 每个 State 字段的公共包装

每个顶层字段使用统一包装：

```json
{
  "status": "observed",
  "observed_at_ms": 15400,
  "evidence": ["用户上半身朝向镜头"],
  "value": {}
}
```

字段说明：

| 属性 | 类型 | 说明 |
|---|---|---|
| `status` | enum | 该字段当前数据状态，见下表 |
| `observed_at_ms` | integer / null | 证据在当前媒体时间轴上的观测时间，不是系统墙钟时间 |
| `evidence` | string[] | 简短、可观察的证据；不得写入无法从输入验证的心理归因 |
| `value` | object / array / string / null | 字段的实际内容 |

`status` 允许值：

| 状态 | 含义 | 典型情况 |
|---|---|---|
| `observed` | 本轮媒体中有直接证据 | 当前画面观察到正面朝向 |
| `retained` | 沿用上轮仍有效的值 | 同一 person_id 持续跟踪，衣着信息沿用 |
| `uncertain` | 有部分证据，但不足以可靠分类 | 脸部可见但表情模糊 |
| `not_visible` | 目标/证据不在有效视野或被遮挡 | 主用户离开画面、脸被遮挡 |
| `not_detected` | 在有效观察区域中未检测到目标/事件 | 当前窗口未观察到动作事件 |
| `not_applicable` | 该字段对当前实体/场景不适用 | 单人场景下的人际关系对 |
| `expired` | 历史值超过有效期 | 旧动作事件已过 TTL |

规则：

- `not_visible` 不等于 `not_detected`。
- `uncertain` 不等于 `平静`、`无` 或 `否`。
- `retained` 必须保留原始 `observed_at_ms`，不得刷新观测时间。
- `expired` 后应清空或显式标记旧值，不得继续参与实时状态判断。
- `valid_until_ms`、`age_ms`、持续时长等派生时间建议由 State Engine 计算，不让生成模型自行估算。

### 3.2 枚举值与置信度的表达规则

**置信度必须绑定到具体枚举槽位，而不是只给整个顶层字段一个笼统分数。** 例如 ATTENTION 同时包含朝向、视线和活动，三者证据强弱可能不同。

单选枚举统一表示为：

```json
{
  "label": "正面",
  "confidence": 0.93
}
```

多选枚举统一表示为数组，每个候选标签单独带置信度：

```json
[
  {"label": "正在打电话", "confidence": 0.96},
  {"label": "正在与他人交流", "confidence": 0.72}
]
```

自由文本字段仍然使用字符串或字符串数组，不强制伪造一个数值置信度。例如 `clothing.description`、`environment_elements`、`relative_to_objects` 和 `description.summary` 都不需要模型自报 0.93 之类的分数；可以保留证据文本和字段 `status`。

置信度的定义：

- 对单选枚举，表示该槽位在允许类别集合中的预测置信度；推荐由分类 logits 经 softmax 得到。
- 对多标签枚举，表示每个标签存在的置信度；推荐由 sigmoid logits 得到，并按类别进行校准。
- `confidence` 是模型输出分数，不天然等于现实世界正确概率。必须在独立标注集上做 temperature scaling / isotonic calibration 等校准，并报告 ECE、Brier Score 或可靠性曲线。
- `uncertain` / `not_visible` 等状态应作为独立类别或状态码处理，不能把低置信度硬映射成“无”。
- 生成式模型自行写出的数字置信度不应直接用于安全阈值或策略门控。未接入可读 logits / 专用 State Head 前，置信度可暂时为 `null`，或者只输出离散的 `high / medium / low` 供调试；不要伪装成校准概率。

下文各字段示例主要展示 `value` 的语义结构。凡是枚举槽位，落地 JSON 时均按上述 `{label, confidence}` 结构包装；自由文本仍保持字符串。

### 3.3 时间单位与时间轴

所有 `*_ms` 均使用媒体时间轴的毫秒数：

- 视频：相对于当前 session/clip 起点的 PTS；
- 音频：相对于同一 session 起点的采样时间；
- ASR turn：通过 `turn_id` 与媒体时间窗关联；
- 不能混用 Unix 时间戳、系统墙钟和媒体 PTS。

模型可以给出粗略事件起止区间；编排层应使用帧 PTS、跟踪器和状态引擎校验。`duration_ms`、`age_ms` 优先由状态引擎根据事件时间计算。

## 4. 八字段定义

## 4.1 ATTENTION —— 朝向、视线与注意力活动

### 设计原则

身体朝向、头部朝向、视线目标和注意力相关活动是正交维度，不应压扁为一个互斥的“8 选 1”枚举。

### `value` 结构

```json
{
  "body_orientation": "正面",
  "head_orientation": "朝向镜头",
  "gaze_target": "注视镜头",
  "activities": ["正在打电话"],
  "description": "用户正对设备打电话，期间偶尔看向镜头。"
}
```

| 槽位 | 建议枚举 |
|---|---|
| `body_orientation` | `正面` / `斜向` / `侧身` / `背对` / `不确定` |
| `head_orientation` | `朝向镜头` / `朝向屏幕其他区域` / `朝向其他人物` / `朝向其他物体` / `背离镜头` / `不确定` |
| `gaze_target` | `注视镜头` / `注视屏幕其他区域` / `注视其他人物` / `注视其他物体` / `视线游移` / `无法判断` |
| `activities[]` | `正在打电话` / `正在操作手机` / `正在与他人交流` / `正在观察物体` / `正在阅读或查看` / `无明显其他活动` / `其他` |

规则：

1. `activities` 是多选数组，可与任何朝向/视线值并存。
2. “面向镜头”不自动等于“注视镜头”。
3. “正在打电话”不自动等于“没有关注设备”；视线和活动应分别判断。
4. 如需一个给策略使用的“设备关注等级”，应由 Agent/策略层根据上述槽位派生，而不是额外让 VLM 生成互相矛盾的结论。

## 4.2 ACTION —— 瞬时动作事件

`ACTION` 表示当前观测窗口内发生过的离散事件，不是当前姿态。没有事件时 `events` 为空数组；无法观察时使用字段包装的 `status` 表达，不能把“不可见”写成“无”。

### `value` 结构

```json
{
  "events": [
    {
      "type": "摇头",
      "count": 2,
      "target_person_id": null,
      "target_object": null,
      "start_ms": 14800,
      "end_ms": 15300,
      "evidence": "头部左右摆动两次"
    }
  ]
}
```

建议 `type` 枚举：

- `点头`
- `摇头`
- `竖大拇指`
- `挥手`
- `鼓掌`
- `指向`
- `举手`
- `伸手或递物`
- `其他`

字段规则：

- `count`：可以可靠计数时输出整数；否则为 `null`，不要猜次数。
- `start_ms` / `end_ms`：媒体时间轴的近似事件范围；精确时间由状态引擎校正。
- `target_person_id` / `target_object`：动作有明确对象时填写，否则为 `null`。
- 1～2 秒内的短暂动作，即便模型解码时动作已经结束，也应在观测窗口覆盖它时报告。
- ACTION 事件不能无限期保留。有效期由 State Engine 配置，例如初始可测试 2～5 秒窗口，必须通过 SOP 回放确定。

## 4.3 EMOTION —— 视觉表情 / 表观情绪

### 定义

`EMOTION` 仅描述从可见面部表情观察到的表观情绪状态，不代表真实心理状态，不允许使用语音内容、语气或 ASR 语义作为证据。

### `value` 结构

```json
{
  "label": "困惑",
  "description": "眉间轻微收紧，眉头略微皱起。"
}
```

建议枚举：

| 值 | 可观察判据（示例，不是充分必要条件） |
|---|---|
| `高兴` | 明显微笑、嘴角上扬等积极表情 |
| `满意` | 放松且带认可意味的积极表情；需与一般微笑区分 |
| `平静` | 面部可见且呈中性表情；不表示内心一定平静 |
| `困惑` | 眉间收紧、眉头内侧上挑、疑惑表情等 |
| `不满` | 轻中度负面表情，但没有明显攻击性或强烈愤怒 |
| `不耐烦` | 明显烦躁、紧锁眉头、急躁表情等 |
| `愤怒` | 强烈愤怒表情线索 |
| `悲伤` | 嘴角下垂、眉部呈悲伤特征等 |
| `惊讶` | 睁大眼睛、张嘴等明显惊讶表情 |
| `其他` | 有明显表情，但不属于上述类别；必须给出描述 |
| `无法判断` | 面部可见，但证据不足以选定类别 |

规则：

- 不要仅凭皱眉就判定“不耐烦”或“愤怒”；应考虑 `困惑` / `不满`。
- `平静` 只能用于观察到中性表情的情况；脸部不可见时使用 `status=not_visible`。
- SOP 08_2（皱眉但语音说“满意”）必须判为视觉上的负面/困惑类，而不是满意。
- 情绪标签边界最终以经人工标注的 SOP 测试集为准。

## 4.4 FEATURE —— 人物可见外观特征

### 设计原则

不建议将 FEATURE 全部枚举化。服装长尾组合很多，应该以自由文本为主，只对下游确实需要的属性增加标准标签。

### `value` 结构

```json
{
  "person_id": "P1",
  "upper_body": {
    "description": "灰色针织毛衣",
    "colors": ["灰色"],
    "garment_type": "毛衣",
    "pattern": "纯色"
  },
  "lower_body": {
    "description": "深色长裤",
    "colors": ["深色"],
    "garment_type": "长裤",
    "pattern": "不确定"
  },
  "attire_style": "休闲",
  "accessories": [
    {"type": "眼镜", "description": "黑框眼镜"}
  ],
  "other_visible_features": ["胸前佩戴工作证"]
}
```

建议槽位：

| 槽位 | 类型 | 建议值 / 说明 |
|---|---|---|
| `upper_body.description` | 自由文本 | 如“灰色针织毛衣” |
| `upper_body.colors[]` | 可选枚举数组 | 黑、白、灰、红、橙、黄、绿、青、蓝、紫、粉、棕、米色、深色、浅色、花色、不确定 |
| `upper_body.garment_type` | 自由文本或小枚举 | T 恤、衬衫、Polo 衫、毛衣、卫衣、夹克、西装外套、大衣、制服等；保留 `其他` |
| `upper_body.pattern` | 可选枚举 | 纯色 / 条纹 / 格子 / 印花 / 其他 / 不确定 |
| `lower_body.description` | 自由文本 | 如“深蓝色牛仔裤” |
| `lower_body.garment_type` | 自由文本或小枚举 | 长裤、短裤、牛仔裤、西裤、半身裙等 |
| `attire_style` | 可选枚举 | 商务正装 / 商务休闲 / 休闲 / 制服 / 运动 / 其他 / 不确定 |
| `accessories[]` | 数组 | 眼镜、墨镜、帽子、口罩、围巾、领带、背包、首饰等，并允许描述补充 |
| `other_visible_features[]` | 自由文本数组 | 工作证、胸牌、手持文件夹等 |

人口属性约束：性别、年龄等不作为默认必判项。只有业务明确需要且经过单独风险评估时，才添加为可选字段；不可见或不确定时不猜测。`attire_style` 不能用于推断职业、雇佣关系或身份。

## 4.5 BEHAVIOR —— 持续姿态与运动状态

`BEHAVIOR` 表示当前持续状态；应与 `ACTION` 的离散事件区分。模型负责识别当前状态和阶段，连续时长优先由 State Engine 根据连续观测计算。

### `value` 结构

```json
{
  "posture": "站立",
  "motion": "远离",
  "phase": "持续中",
  "direction": "远离镜头",
  "relative_speed": "缓慢",
  "duration_ms": null,
  "description": "用户保持站立并持续缓慢远离镜头。"
}
```

| 槽位 | 建议枚举 |
|---|---|
| `posture` | 站立 / 坐 / 蹲 / 弯腰 / 行走 / 其他 / 不确定 |
| `motion` | 静止 / 行走 / 靠近 / 远离 / 转身 / 横向移动 / 无明显移动 / 其他 / 不确定 |
| `phase` | 开始 / 持续中 / 结束 / 不确定 |
| `direction` | 朝向镜头 / 远离镜头 / 向左 / 向右 / 朝向某人物 / 远离某人物 / 不确定 |
| `relative_speed` | 缓慢 / 正常 / 快速 / 不确定 |

规则：

- `duration_ms` 是 State Engine 派生字段，模型可不填或输出 `null`。
- 不经相机标定和跟踪，不输出米/秒等精确速度或距离。
- “保持不动”应表达为 `motion=无明显移动`，不能与“没有观察到用户”混淆。
- 行为状态的开始、持续和结束应依赖时间连续性与滞回，而不是单帧判断。

## 4.6 RELATION —— 多人场景与互动关系

### 设计原则

必须把“直接可观察的社交空间事实”与“关系类型推断”拆开。并排站立不等于同事；两人相邻不等于陪同。

### `value` 结构

```json
{
  "visible_person_count": 2,
  "people": [
    {"person_id": "P1", "frame_region": "中央"},
    {"person_id": "P2", "frame_region": "右侧"}
  ],
  "pairs": [
    {
      "person_a": "P1",
      "person_b": "P2",
      "distance_category": "正常社交距离",
      "formation": "并排",
      "interaction_observed": "不确定",
      "inferred_relationship": "不确定",
      "evidence": "两人并排站立，未观察到明确交谈动作。"
    }
  ],
  "primary_interaction_target": "P2"
}
```

建议槽位：

| 槽位 | 建议值 |
|---|---|
| `visible_person_count` | 整数；对外可派生 1人 / 2人 / 3人及以上 |
| `distance_category` | 近距离 / 正常社交距离 / 较远 / 不可估 |
| `formation` | 并排 / 面对面 / 前后 / 分散 / 其他 / 不可估 |
| `interaction_observed` | 是 / 否 / 不确定 |
| `inferred_relationship` | 同行 / 陪同 / 主客 / 同事 / 路人 / 其他 / 不确定 |
| `primary_interaction_target` | person_id / 设备或镜头 / 画面外 / 无 / 不确定 |

规则：

- person_id 应由人脸/人体跟踪系统维护，不应仅凭左右位置在每轮重新创建身份。
- 距离等级只表示画面中的相对空间关系，不是精确米制距离。
- `inferred_relationship` 只有存在足够互动行为、角色线索或上下文证据时才输出确定类别，否则为“不确定”。
- 多人场景建议用 `pairs[]` 表示关系，避免把所有人压成一个关系标签。

## 4.7 ENV —— 视觉环境

### `value` 结构

```json
{
  "scene_type": "室内展厅",
  "lighting": "正常",
  "other_person_count": 1,
  "environment_elements": ["玻璃展柜", "展示海报", "展台"],
  "description": "用户位于室内展厅，周围有多个展示展台。"
}
```

| 槽位 | 建议枚举 |
|---|---|
| `scene_type` | 室内展厅 / 室内办公 / 室内会议室 / 室内走廊 / 室内家居 / 室内商业 / 室外街道 / 室外广场 / 室外自然 / 车内 / 其他 / 不确定 |
| `lighting` | 明亮 / 正常 / 偏暗 / 逆光 / 强光 / 不确定 |
| `other_person_count` | 整数或 `null`（不可观察时） |
| `environment_elements[]` | 自由文本数组：物品、海报、展台、门窗、家具等 |
| `description` | 自由文本，对场景做简短补充 |

噪声、嘈杂程度、SNR、突发噪声等不属于视觉 ENV，归音频侧状态。

## 4.8 POSITION —— 人物画面位置及物体相对位置

### `value` 结构

```json
{
  "person_id": "P1",
  "frame_region": "中央",
  "bbox_xyxy_norm": [0.32, 0.12, 0.68, 0.95],
  "camera_distance_appearance": "中",
  "relative_to_objects": ["位于展台左侧"],
  "referenced_objects": [
    {"object": "桌上的水杯", "relation": "指向"}
  ]
}
```

| 槽位 | 建议枚举 / 类型 |
|---|---|
| `frame_region` | 左上 / 上中 / 右上 / 左中 / 中央 / 右中 / 左下 / 下中 / 右下 / 不确定 |
| `bbox_xyxy_norm` | 可选归一化检测框 `[x1,y1,x2,y2]`，范围 0～1；优先由检测器给出 |
| `camera_distance_appearance` | 近（半身为主） / 中（全身为主） / 远（人物较小） / 不可估 |
| `relative_to_objects[]` | 自由文本，如“位于玻璃门左侧” |
| `referenced_objects[]` | 物体名称 + 关系（指向、拿起、持有、靠近、位于其左侧等） |

规则：

- bbox 和 person_id 优先使用检测/跟踪模块的输出；VLM 可补充物体语义关系。
- 画面占比不能直接等同于真实物理距离。
- 云台角度、世界坐标、精确距离和导航障碍物定位应由检测、几何标定或专用定位模块负责。

## 5. 状态生命周期与合并规则

### 5.1 推荐的初始 TTL（仅用于回放调参，不是固定标准）

| 字段 | 初始 TTL 建议 | 说明 |
|---|---:|---|
| ATTENTION | 1～3 秒 | 注意力容易变化，需较快刷新 |
| ACTION | 2～5 秒事件窗口 | 事件保留窗口，过期后删除 |
| EMOTION | 1～3 秒 | 面部表情短时变化 |
| FEATURE | 30～120 秒 | 同一 person_id 且跟踪连续时可沿用 |
| BEHAVIOR | 由连续观测决定 | 依赖开始/持续/结束检测，不只依赖固定 TTL |
| RELATION | 5～10 秒 | 人员组合或互动发生变化时刷新 |
| ENV | 10～30 秒 | 场景切换、镜头切换时刷新 |
| POSITION | 每轮/每帧更新 | 依赖检测框和画面坐标 |

这些时间值必须用 SOP 录像回放和线上错误日志校准，不能直接当产品常量。

### 5.2 State Engine 合并伪规则

1. 先按 `person_id` 关联当前人物，无法确认同一人时不继承该人的 FEATURE / BEHAVIOR / RELATION。
2. `observed` 覆盖旧值，并记录新的 `observed_at_ms`。
3. `retained` 保留旧值和原始观测时间，不刷新时间戳。
4. `uncertain` 不应自动覆盖一个仍然有效且证据更强的值；由字段策略决定保留、降级或标记冲突。
5. `not_visible` 不能被解释成 `ACTION=无` 或 `EMOTION=平静`。
6. ACTION 作为事件列表合并，按 event 时间与类型去重；过 TTL 后移除。
7. BEHAVIOR 的 `duration_ms` 由 State Engine 根据连续状态段计算；状态变化时结束旧段并启动新段。
8. `expired` 状态不得继续作为实时决策的正向证据。

## 6. Omni-Jev 的 State 输出契约

### 6.1 Omni-Jev 的职责边界

本文所称 **Omni-Jev** 不是 Agent 策略决策器，也不需要每轮接收一组自然语言问题。它的唯一任务是：

1. 接收当前原始音频、视频，以及必要的 ASR 文本和上一轮 State 快照；
2. 生成自然语言交互状态描述；
3. 对 Schema 2.0 中每个可枚举槽位选择当前类别，并输出该类别的置信度；
4. 对自由文本槽位生成细节描述；
5. 全量输出 8 个顶层 State 字段及字段状态元数据。

它**不负责**判断“是否应该打断”“是否应该主动发起对话”“下一步采取什么策略”等业务动作。这些策略由下游 Interaction Policy / Agent 根据 State 决定。

### 6.2 统一输出结构

```json
{
  "schema_version": "2.0",
  "session_id": "session-001",
  "turn_id": "turn-012",
  "media_window": {
    "start_ms": 12000,
    "end_ms": 15800
  },
  "description": {
    "summary": "用户正面向设备，短暂看向旁边的人后又看回屏幕。",
    "visual": "用户穿灰色针织上衣，戴黑框眼镜。",
    "audio": "用户正在说话，具体语音识别文本由 ASR 模块提供。"
  },
  "state": {
    "ATTENTION": {
      "status": "observed",
      "observed_at_ms": 15400,
      "evidence": ["上半身朝向镜头，视线回到镜头区域"],
      "value": {
        "body_orientation": {"label": "正面", "confidence": 0.94},
        "gaze_target": {"label": "注视镜头", "confidence": 0.86},
        "activities": []
      }
    },
    "ACTION": {},
    "EMOTION": {},
    "FEATURE": {},
    "BEHAVIOR": {},
    "RELATION": {},
    "ENV": {},
    "POSITION": {}
  }
}
```

示例中的空对象只为缩短篇幅；真实输出必须包含完整 8 个字段及其合法 `status`、`value`。不包含 `questions`、`decisions`、`option_id` 或策略结论。

### 6.3 字段级输出规则

- 每轮全量输出 8 个顶层字段。
- 每个枚举子槽必须从该槽位白名单中选择一个值；多标签槽位按定义输出数组。
- 每个枚举值必须有对应的置信度；对自由文本不要求伪造数值置信度。
- `ACTION.events[]` 中每个事件类型分别附带置信度；事件次数和时间区间可为空，不可靠时不要猜测。
- `EMOTION` 必须只使用视觉证据。实现层应通过视觉专属 State Head / 视觉 token 证据路径，或专项训练与对照测试，尽量避免音频信息污染该槽位。
- `FEATURE`、`ENV.environment_elements`、`POSITION.relative_to_objects` 等自由文本槽位由语言模型生成。
- `RELATION.inferred_relationship` 是推断而非直接事实，低证据时必须选择“不确定”并降低置信度。

### 6.4 置信度的实现等级

| 等级 | 实现方式 | 置信度可用性 | 定位 |
|---|---|---|---|
| L0 | Prompt 让模型自报数值 confidence | 不可靠，不应用于阈值 | 仅用于快速验证输出格式，不推荐上线 |
| L1 | 对受约束的枚举标签读取 LM logits / token logprobs，并在允许类别内归一化 | 可作为初始分数，仍需校准 | 低改造过渡方案；需验证当前 vLLM-Omni WebSocket 路径能否暴露所需 logits/logprobs |
| L2 | 在 Qwen3-Omni Thinker 共享隐藏状态上增加 State Head | 可训练、可校准 | 推荐目标方案 |

L1 若使用短标签代码，必须验证其 tokenizer 编码为单 token，或正确计算多 token label 的条件序列概率。不可直接将整段文本的平均 logprob 当作该类别的置信度。

### 6.5 下游策略接口

Interaction Policy 只消费 `state`，按自己的规则计算策略。例如“是否适合主动发起对话”应由 Agent 综合 ATTENTION、ACTION、EMOTION、RELATION 等状态判断；它不是 Omni-Jev 的输出字段，也不应混入本 Schema。

## 7. Qwen3-Omni 的生成与流式输入建议

- 一个 ASR 话轮触发一次统一的多模态 State 更新请求；请求中不再附带问题列表。
- 固定 system prompt 和 Schema 词表放在稳定前缀，当前媒体窗口、ASR 文本、上一轮 State 放在变化后缀。
- 输出包括 `description` 和完整 `state`；先输出短 `description.summary`，随后输出枚举 State，再输出较长自由文本细节，具体顺序按下游首包需求调整。
- 当前增量视频 Prefill 可继续沿用；但自定义 State Head 需要从 Thinker 推理路径读取所需隐藏状态，并接入 vLLM-Omni stage 输出/后处理。不能认为现有 WebSocket `response.text.delta` 会自动返回分类 logits。
- 如果暂时不修改 vLLM-Omni，先使用受约束 JSON 生成验证描述与枚举的准确性；置信度先置 `null`。这比让模型编造置信度更可靠。
- State Head 的媒体窗口应与 LM Head 使用同一时间窗、同一帧采样和同一音视频同步策略；不得让两个输出分支看到不同的媒体证据。

## 8. 原有 SOP 的回归重点

以下测试应保留，并为每条样本同时标注描述、8 字段 State、枚举子槽标签和可观察证据：

| SOP | 核心检查 | 2.0 需要验证的点 |
|---|---|---|
| 06_1 / 06_2 | 背对、侧身、打电话、偶尔看屏幕 | ATTENTION 正交槽位是否能正确组合 |
| 07_1 / 07_2 | 竖大拇指、摇头次数 | ACTION 是否记录短暂事件和次数 |
| 08_1 / 08_2 | 皱眉、困惑、语音与表情相反 | EMOTION 是否严格只看视觉 |
| 09 | 毛衣、职业装 | FEATURE 是否保留长尾细节，避免无证据人口属性推断 |
| 10_1 / 10_2 | 持续远离、持续时长 | BEHAVIOR phase 和 State Engine 时长计算 |
| 11 | 两人关系、社交距离、交互对象 | RELATION 是否拆分事实与推断 |

新增建议：

- 遮挡、离开画面、重新进入画面；
- 单人变双人、双人变多人，person_id 关联变化；
- 视觉表情与语音情绪冲突；
- 相同状态在不同业务策略规则下如何被下游使用（本 Schema 本身不输出策略结论）；
- 视频帧丢失、时间戳乱序和音视频不同步；
- 旧 ACTION 不能在数个 ASR turn 后重复触发。

测试集建议按人、session、完整视频切分，不要把同一段视频的相邻帧随机分到训练集和测试集。

## 10. 核心验收标准

- [ ] 每次输出必须包含完整的 8 个 State 顶层字段。
- [ ] 每个字段必须带合法 `status`。
- [ ] 枚举值必须通过白名单校验；未知值不得静默归一化。
- [ ] `ACTION` 是事件，`BEHAVIOR` 是持续状态，二者不互相替代。
- [ ] `EMOTION` 只基于视觉表情，不参考 ASR 文本和语音情绪。
- [ ] `RELATION` 区分观察事实与关系推断。
- [ ] `FEATURE`、`ENV`、`POSITION` 保留必要的自由文本长尾信息。
- [ ] 时间戳统一采用媒体时间轴；保留状态不刷新原始观测时间。
- [ ] 每个枚举槽位输出独立 confidence；自由文本不伪造数值概率。
- [ ] “不可见 / 未检测到 / 不确定 / 无 / 不适用 / 过期”具有不同含义。
- [ ] SOP 06～11 全部通过回归，并对错误样本归因到感知、Schema、时间跟踪或输出格式。

## 附录 A：枚举槽位设计规范

1. 每个枚举槽位只表达一个可观察维度，避免把多个正交维度合并为组合枚举。
2. 枚举值应互斥、可观察、覆盖常见场景，并保留 `不确定` / `其他` 等兜底项。
3. 明确每个槽位的证据模态：例如 EMOTION 仅视觉，语音情绪不进入该字段。
4. 对多标签槽位明确其为多选而非单选，并为每个标签单独输出 confidence。
5. 置信度只对枚举标签输出；自由文本描述不要求模型自报概率。
